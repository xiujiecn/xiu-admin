### 1.3 GoFrame 分层架构核心规则

```
请求流程:
  Client Request
    → Router (路由分组 + 中间件绑定)
    → Middleware Chain (Ctx → ResponseHandler → CORS → Auth)
    → Controller (参数接收，调用 Service)
    → Service Interface (接口定义，由 Logic 实现)
    → Logic (核心业务逻辑)
    → DAO + Model (数据库操作)
    → Response (统一 JSON 包装)
```

**关键约定**：

| 规则 | 说明 |
|------|------|
| Service 自注册 | `logic` 通过 `init()` 调用 `service.Register*()` 自注册，Controller 通过 `service.*()` 获取单例 |
| DAO 禁止手动编辑 | `dao`、`do`、`entity` 由 GoFrame gf gen 自动生成，修改表结构后重新生成 |
| 数据载体规范 | ORM 操作必须使用 `dao`/`do` 结构体，禁止使用 `g.Map` 或 `map[string]interface{}` |
| 错误封装 | 业务错误统一使用 `gerror.New()` / `gerror.Newf()` 封装 |
| 软删除 | ORM 自动维护 `deleted_at`，逻辑删除统一调用 DAO 的 `Delete()` 方法 |
| 时间字段 | `created_at`、`updated_at` 由 ORM 自动维护，无需手动赋值 |

### 1.4 前端分层架构核心规则

```
请求流程:
  用户交互
    → View (页面视图, .vue)
    → v-access:code (权限指令控制按钮显隐)
    → API 函数 (api/*.ts → requestClient.post/get)
    → RequestClient (三层拦截器: 业务状态码 → token刷新 → 错误消息)
    → 后端 API
    → 响应拦截器 (code===0 成功 / code===61 登录超时)
    → View 更新
```

**关键约定**：

| 规则 | 说明 |
|------|------|
| 代码四层分离 | 接口请求 → `src/api`，页面视图 → `src/views`，路由 → `src/router`，状态 → `src/store` |
| 权限指令统一 | 按钮权限用 `v-access:code="'cpm:xxx'"`，条件控制用 `hasAccessByCodes()` |
| API 封装 | 所有请求通过 `requestClient`，禁止自行创建 Axios 实例 |
| 组件复用优先 | 优先使用 `@vben/common-ui`、`@vben/hooks` 等内置包，避免新增第三方依赖 |
| 图标规范 | 统一使用 Iconify 图标命名，已有图标时禁止自定义绘制 |
| 页面风格 | 管理类页面：紧凑信息、表格为主、抽屉/弹窗编辑，禁止营销风大横幅 |

## 二、权限控制体系

> 这是系统最核心、最复杂的部分，请务必深入理解。

### 2.1 权限模型概览：RBAC + 多维度权限码 + 数据范围

```
用户(User)
  → 角色(Role) [多对多]
    → 菜单(Menu) [多对多]
      → 权限标识(perms) [如 "system:user:add"]

权限码由 6 种维度叠加:
  cpr:角色标识      — 角色权限码
  cpm:菜单权限标识   — 菜单权限码
  cpd:部门编码      — 部门权限码
  cpp:岗位编码      — 岗位权限码
  cpu:用户名        — 用户权限码
  cpc:current:user  — 当前登录用户默认权限码
```

**超级管理员特殊规则**：角色ID=1 的用户直接拥有所有权限，无需计算权限码。

### 2.2 认证流程：JWT + Redis 双重校验

#### 登录流程

```
1. 前端: 密码 MD5 加密 → POST /system/auth/login {username, password, captchaId, captchaValue, tenantId}
2. 后端: 验证码校验 → 用户名密码验证(带租户隔离) → 构造 JWT Claims
3. JWT Claims 包含: UUID, userId, username, nickName, deptId, tenantId, roles[], loginAt
4. 生成 HS256 签名 Token → 存入 Redis (支持服务端主动踢出)
5. 前端: 存储 accessToken → 并行获取 userInfo + accessCodes → 跳转首页
```

#### Token 校验流程

```
每次请求:
  → Ctx 中间件从 Authorization Header 提取 Token
  → JWT 解析 Claims (签名验证 + 过期检查)
  → Redis 反向校验 (检查 Token 是否被服务端删除/拒绝)
  → 注入 model.Context 到请求上下文 (userId, deptId, tenantId, roles)
```

#### 强制下线机制

```
管理员踢出用户:
  → 解析目标 Token 获取 UUID
  → Redis: DelSysAuthToken (删除正常 Token)
  → Redis: SetSysAuthTokenReject (加入拒绝列表)
  → 用户下次请求: Auth 中间件检测到拒绝列表 → 返回"已被强制下线"
```

**关键代码位置**：

| 文件 | 路径 | 说明 |
|------|------|------|
| 认证逻辑 | `server/internal/logic/system/sys_auth.go` | Login/GenerateToken/ParseToken/DeleteToken |
| JWT Claims | `server/internal/model/sys_auth.go` | BaseClaims/CustomClaims 结构体 |
| 权限码计算 | `server/internal/logic/system/sys_auth.go` | GetUserAccessCodeList |
| 权限码常量 | `server/internal/consts/system.go` | cpr/cpm/cpd/cpp/cpu/cpc 前缀 |
| Redis 缓存 | `server/internal/library/bcache/` | Token 存取/拒绝列表 |

### 2.3 Auth 中间件鉴权流程

```
请求进入 Auth 中间件:
  1. 豁免路径检查 → IsExceptLogin (从配置 router.exceptLogin 读取白名单)
  2. 用户ID校验 → 从上下文获取，无则返回"未登录"
  3. 强制下线检查 → bcache.GetSysAuthTokenReject (检查拒绝列表)
  4. 超级管理员放行 → roleId==1 直接通过
  5. 权限码匹配:
     a. 从 Handler 的 MetaTag 获取 "x-check-permission"
     b. 解析为权限码列表 (逗号分隔, & 组合表示需同时满足)
     c. 与用户缓存的 accessCodeList 做交集匹配
     d. 匹配成功 → 将当前角色的 dataScope 写入上下文
     e. 匹配失败 → 返回"无权限"
```

**路由定义中绑定权限码**：

```go
// 示例: 在路由注册时通过 MetaTag 绑定权限码
group.Bind(
    controller.System.User.NewV1(),
)
// Handler 的 MetaTag 注解: "x-check-permission" = "cpm:system:user:add"
```

### 2.4 数据范围过滤 (Data Scope)

> 这是权限体系中最容易忽略但极其重要的一环：不同角色看到的数据范围不同。

| 范围代码 | 名称 | SQL 过滤方式 | 适用场景 |
|---------|------|-------------|---------|
| 1 | 全部数据 | 不过滤 | 超管/全局管理员 |
| 2 | 自定义数据 | WHERE dept_id IN (自选部门) | 需要灵活控制可见范围 |
| 3 | 本部门 | WHERE dept_id = 当前用户dept_id | 部门主管 |
| 4 | 本部门及以下 | WHERE dept_id IN (本部门+所有子部门) | 分管领导 |
| 5 | 仅本人 | WHERE created_by = 当前用户ID | 普通员工 |
| 6 | 本部门及以下或本人 | WHERE dept_id IN(...) OR created_by=uid | 主管也能看自己创建的 |
| 7 | 本组织及下一级 | WHERE dept_id IN (公司+直接下级) | 集团层面管理 |

**自动注入机制**：通过 GORM Model Handler (`xgorm/handler/filter_auth.go`) 自动注入 WHERE 条件：

```go
// Service 层只需这样写:
m := dao.SysUser.DB().Model(dao.SysUser.Table())
// FilterAuth 自动根据当前用户的数据范围注入 WHERE 条件
// 无需手动写 WHERE dept_id = xxx
```

**关键代码位置**：

| 文件 | 路径 | 说明 |
|------|------|------|
| 数据范围过滤 | `server/internal/library/xgorm/handler/filter_auth.go` | FilterAuth 函数 |
| Handler 配置 | `server/internal/library/xgorm/handler/handler.go` | FilterAuth/FilterTenant 选项 |
| 部门树查询 | 同上 | 递归查询子部门 ID 列表 |

### 2.5 多租户数据隔离

```go
// 自动注入机制: 如果表有 tenant_id 字段，Model Handler 自动添加 WHERE tenant_id = 当前租户
// 无需手动处理租户过滤
func FilterTenant(m *gdb.Model) *gdb.Model {
    if gstr.InArray(fields, "tenant_id") {
        m = m.Where("tenant_id", contexts.GetTenantId(ctx))
    }
}
```

### 2.6 前端权限控制

#### 动态菜单加载

```
登录成功 → 并行获取:
  1. userInfo → GET /system/user/info → userStore.setUserInfo
  2. accessCodes → GET /system/auth/get-access-codes → accessStore.setAccessCodes
  3. menuList → GET /system/menu/all → 合并本地路由 → generateAccessible → 生成可访问菜单+路由
```

权限模式: `backend`（后端控制菜单和路由），配置在 `preferences.ts` 中 `app.accessMode: 'backend'`。

#### 按钮级权限指令

```vue
<!-- 方式一: v-access:code 指令 — 无权限时直接移除 DOM 元素 -->
<a-button v-access:code="'cpm:system:user:add'">新增用户</a-button>
<a-button v-access:code="'cpm:system:user:edit'">编辑</a-button>
<a-button v-access:code="'cpm:system:user:remove'">删除</a-button>

<!-- 方式二: hasAccessByCodes 函数 — 用于条件禁用/显示 -->
<a-switch :disabled="!hasAccessByCodes(['cpm:system:user:edit'])" />

<!-- 方式三: v-access:role 指令 — 基于角色判断 (仅 frontend 模式下生效) -->
<a-button v-access:role="'admin'">管理员操作</a-button>
```

**权限码命名规范**: `cpm:{模块}:{实体}:{动作}`
- `cpm:system:user:add` — 系统管理-用户-新增
- `cpm:system:role:edit` — 系统管理-角色-编辑
- `cpm:monitor:online:batchLogout` — 监控-在线用户-批量下线

#### 路由守卫认证流程

```
路由守卫 (guard.ts):
  1. 核心路由 (登录页等) → 直接放行
     - 已登录且访问登录页 → 重定向到首页
  2. 无 accessToken →
     - meta.ignoreAccess=true → 放行
     - 否则 → 重定向到 /auth/login?redirect=目标页
  3. 有 token 但未生成路由 →
     - fetchUserInfo()
     - generateAccess() → 获取菜单+权限码 → 生成动态路由
     - isAccessChecked = true → 重定向到目标页
  4. 有 token 且已生成路由 → 直接放行
```

### 2.7 权限缓存机制

| 缓存层 | Key | TTL | 用途 |
|--------|-----|-----|------|
| 内存缓存 (mcache) | `user_access_code_list_{userId}` | 24h | 权限码列表 |
| 内存缓存 (mcache) | `user_role_data_access_code_list_{userId}` | 24h | 角色+数据范围权限码 |
| Redis 缓存 (bcache) | `sys_auth_token_{userId}_{uuid}` | Token 有效期 | JWT Token 存储 |
| Redis 缓存 (bcache) | `sys_auth_token_reject_{userId}_{uuid}` | Token 有效期 | 强制下线拒绝列表 |

**缓存失效**: 监听事件 (`EventKeyUserLogout`) → 清除用户权限缓存。

## 三、定时任务机制

### 3.1 双引擎架构

项目采用两种任务调度引擎，各有适用场景：

| 引擎 | 实现 | 适用场景 | 特点 |
|------|------|---------|------|
| 内置 Cron | `robfig/cron/v3` | 轻量级周期任务 | 单实例运行、秒级表达式、反射调用 |
| Asynq | `xiujiecn/asynq` (Redis) | 分布式/延迟/一次性任务 | 多实例负载均衡、分组聚合、失败重试 |

### 3.2 内置 Cron 任务

#### 架构

```go
// Tasks 结构体
type Tasks struct {
    cron    *cron.Cron           // robfig/cron v3 引擎
    lock    sync.Mutex
    taskMap map[string]*taskInfo  // uid -> taskInfo 映射
}
```

#### 内置任务注册

```go
// server/internal/tasks/clear_data.go
func init() {
    RegisterInnerTask("clear_operation_log_by_days", "ClearOperationLogByDays")
    RegisterInnerTask("test", "Test")
}

// 通过 init() 在程序启动时注册内置任务名→方法名映射
// 实际方法定义在 Task 结构体上，运行时通过反射调用
func (t Task) ClearOperationLogByDays(days string) { ... }
```

#### 反射调用机制

```go
// CallMethod: 通过方法名反射调用 Task 结构体上的方法
// 支持参数传递: 方法参数从任务配置的 params 字段解析
// 支持并发控制: Concurrent 字段控制是否允许同一任务并发执行
// 支持超时: Timeout 字段限制任务最大执行时间
```

#### 数据库管理任务

```go
// 系统管理员在后台页面配置定时任务 → 存入 sys_job 表
// 启动时: service.SysJob().InitRegister() 从数据库加载所有 status=正常的任务并注册
// 任务启动流程:
//   1. 检查方法名是否存在于 innerTaskNames
//   2. 解析参数
//   3. 构造 Task 数据 → JSON 序列化
//   4. 周期任务 → TasksInstance.Cron
//   5. 单次任务 → TasksInstance.Once

// 任务停止: 从 taskMap 中 Remove
// 任务重启: taskStop + taskRun
```

#### 启动初始化

```go
// cmd/http.go 中通过 inithttp.RegisterHttpInitFunc 注册
inithttp.RegisterHttpInitFunc("initJobTask", initJobTask)

func initJobTask(ctx) error {
    tasks.TasksInstance(ctx)        // 创建 cron 实例
    service.SysJob().InitRegister() // 从 DB 加载任务
}
```

### 3.3 Asynq 分布式任务

#### 架构

```go
type Worker struct {
    client    *asynq.Client     // 生产者: 创建任务
    inspector *asynq.Inspector  // 管理器: 查看任务状态
    scheduler *asynq.Scheduler  // 调度器: 周期任务调度
    svr       *asynq.Server     // 消费服务器: 执行任务
}
```

#### 任务类型

| 类型 | 方法 | 说明 |
|------|------|------|
| 周期任务 | `Cron` | 定期执行 (cron 表达式) |
| 一次性任务 | `Once` | 立即或延迟执行一次 |
| 延迟任务 | `Once` + delay | 指定延迟时间后执行 |
| 分组聚合 | `GroupAggregator` | 短时间内同组任务合并执行 |

#### 消费者注册

```go
// server/internal/queues/base.go
func RegisterQueueProcess(name string, process worker.Process) {
    processes[name] = &process
}

// 各业务模块通过 init() 注册消费者
// server/internal/queues/ 目录下的文件在编译时通过 init() 自动注册
```

**关键代码位置**：

| 文件 | 路径 | 说明 |
|------|------|------|
| Cron 引擎 | `server/internal/tasks/tasks.go` | Tasks 结构体/创建/管理 |
| 内置任务 | `server/internal/tasks/clear_data.go` | 任务注册+实现 |
| 数据库任务 | `server/internal/logic/system/sys_job.go` | InitRegister/taskRun/taskStop |
| Asynq Worker | `server/internal/library/worker/worker.go` | Worker 结构体/初始化 |
| Asynq 队列 | `server/internal/queues/base.go` | 消费者注册/启动 |

### 3.4 新增定时任务的步骤

**场景A: 添加内置任务**:

1. 在 `server/internal/tasks/` 下新建文件 (如 `my_task.go`)
2. 在 `init()` 中注册: `RegisterInnerTask("task_name", "MethodName")`
3. 在 `Task` 结构体上定义方法: `func (t Task) MethodName(params string) { ... }`
4. 在数据库 `sys_job` 表中配置任务 (通过后台管理页面)

**场景B: 添加 Asynq 任务**:

1. 在 `server/internal/queues/` 下新建消费者文件
2. 定义 `worker.Process` 结构体，实现 `Handler` 方法
3. 在 `init()` 中通过 `RegisterQueueProcess` 注册
4. 在业务代码中通过 `service.Worker().Cron/Once` 创建任务

## 四、队列处理架构

### 4.1 双队列系统

项目有两条消息通道，各自有明确的适用场景：

| 通道 | 实现 | 适用场景 | 特点 |
|------|------|---------|------|
| Utility 队列 | 内存队列 + Redis 队列 | 请求级异步处理 (如操作日志) | 轻量、快速、无持久化(内存)/有持久化(Redis) |
| Internal 队列 | Asynq Worker | 分布式后台任务 | Redis 持久化、失败重试、分组聚合 |

### 4.2 Utility 队列 (请求级异步处理)

#### 核心接口

```go
// server/utility/queue/queue.go
type Process interface {
    GetTopic() string                           // 消费主题
    GetType() QueueType                         // 队列类型 (memory/redis)
    Handle(ctx context.Context, p Payload) error // 处理逻辑
}

type Payload struct {
    Ts       string           // 时间戳
    TraceId  string           // 链路追踪ID
    Topic    string           // 主题
    Data     json.RawMessage  // 业务数据
    Expire   int64            // 过期时间
    ClientId string           // 客户端标识 (广播时使用)
}
```

#### 两种队列实现

| 实现 | 文件 | 说明 |
|------|------|------|
| 内存队列 | `utility/queue/memory_queue.go` | 基于 `gqueue.Queue` + `grpool` 协程池 |
| Redis 队列 | `utility/queue/redis_queue.go` | 基于 GoFrame Redis + `grpool` |
| Redis 广播 | `utility/queue/redis_broadcast.go` | 跨进程广播推送 |

#### 业务队列示例: 操作日志

```go
// server/internal/queues/httpqueues/sys_opt_log_queue.go

func init() {
    inithttp.RegisterHttpInitFunc("init "+consts.QueueSysOptLog, func(ctx context.Context) error {
        // 创建消费者 (100 workers)
        queue.NewConsumer(gctx.New(), SysOptLogQueue, &queue.Config{Workers: 100})
        // 创建生产者
        queue.NewProducer(gctx.New(), queue.QueueTypeMemory, consts.QueueSysOptLog, &queue.Config{})
        return nil
    })
}

// 消费处理: 操作日志异步写入数据库
func (q *qSysOperLog) Handle(ctx context.Context, p queue.Payload) error {
    var data entity.SysOperLog
    json.Unmarshal(p.Data, &data)
    return service.SysOperLog().RealWrite(ctx, data)
}
```

**生产者调用** (中间件):

```go
// server/internal/logic/middleware/middleware.go
func (s *sMiddleware) OperationLog(r *ghttp.Request) {
    data, _ := service.SysOperLog().AnalysisLog(ctx)
    queue.Push(r.GetCtx(), consts.QueueSysOptLog, data)  // 非阻塞推送
}
```

### 4.3 Internal 队列 (Asynq 分布式任务)

#### 架构

```
生产者 (asynq.Client):
  service.Worker().Cron/Once → 创建 Task → 推入 Redis

消费者 (asynq.Server):
  RegisterQueueProcess → 注册 Handler → asynq.Server 拉取执行

调度器 (asynq.Scheduler):
  周期任务 → cron 表达式 → 定时推送 Task
```

#### 消费者注册

```go
// server/internal/queues/base.go
var processes = map[string]*worker.Process{}

func RegisterQueueProcess(name string, process worker.Process) {
    processes[name] = &process
}

func Run(ctx context.Context) {
    for name, process := range processes {
        queues[name] = worker.RegisterQueueProcess(*process) // 创建 Asynq Worker
    }
}
```

### 4.4 队列选型指南

| 场景 | 推荐 | 原因 |
|------|------|------|
| 操作日志异步写入 | 内存队列 | 请求级、高频、无需跨进程 |
| 数据同步/通知推送 | Redis 队列 | 需要跨进程可靠传递 |
| 定时数据清理 | Cron (内置) | 轻量周期任务 |
| 分布式批处理 | Asynq | 需要失败重试、负载均衡、分组聚合 |

**关键代码位置**：

| 文件 | 路径 | 说明 |
|------|------|------|
| 队列接口 | `server/utility/queue/queue.go` | Process/Payload/Producer/Consumer |
| 内存队列 | `server/utility/queue/memory_queue.go` | gqueue+grpool 实现 |
| Redis 阙列 | `server/utility/queue/redis_queue.go` | Redis+grpool 实现 |
| 操作日志队列 | `server/internal/queues/httpqueues/sys_opt_log_queue.go` | 实际业务示例 |
| Asynq Worker | `server/internal/library/worker/worker.go` | 分布式队列核心 |

## 五、WebSocket 实时通信

### 5.1 架构概览

```
WebSocket 服务器 (gorilla/websocket)
  │
  ├── ClientManager (连接管理器)
  │     ├── Clients map[*Client]bool       # 所有连接
  │     ├── Users map[string]*Client        # 已登录用户 (ws_{userId})
  │     ├── Register chan *Client            # 连接注册通道
  │     ├── Unregister chan *Client          # 断开通道
  │     ├── Broadcast chan *WResponse        # 全体广播
  │     ├── TagBroadcast chan *TagWResponse  # 标签广播
  │     ├── UserBroadcast chan *UserWResponse    # 用户广播
  │     └── ClientBroadcast chan *ClientWResponse # 单客户端广播
  │
  ├── Client (单个客户端)
  │     ├── Socket *websocket.Conn   # gorilla 连接
  │     ├── Send chan *WResponse     # 发送缓冲 (容量100)
  │     ├── UserId uint64            # 登录后绑定
  │     ├── tags *garray.StrArray    # 订阅标签 (分组广播)
  │     ├── read() goroutine         # 读取消息
  │     └── write() goroutine        # 发送消息
  │
  └── 心跳管理
        ├── ping(): 每1分钟全体 ping
        └── 清理: 每30秒检查, 6分钟无心跳断开
```

### 5.2 消息协议

```json
// 客户端发送: JSON 格式
{ "e": "事件名", "d": "数据" }

// 事件类型:
login    — 用户登录绑定 (d: userId)
join     — 加入标签组 (d: "ws:tag:xxx")
quit     — 退出标签组
joins    — 批量加入标签组 (d: {names: ["tag1", "tag2"]})
quits    — 批量退出标签组
ping     — 客户端心跳
is_app   — APP标识
```

### 5.3 标签广播机制

> 这是 WebSocket 的核心设计：通过标签(Tags)实现分组定向推送。

```
1. 客户端连接 → 发送 login 绑定 userId
2. 客户端发送 join/joins → 加入指定标签组 (如 "ws:tag:monitor:server")
3. 服务端推送:
   - SendToTag → 向指定标签的所有订阅客户端推送消息
   - SendToUser → 向指定 userId 的客户端推送
   - Broadcast → 向所有连接推送
4. 监控数据推送示例:
   RunMonitor() 每5秒采集 → SendToTag(WSTagMonitorServer, {event: "monitor:host", data: hostInfo})
```

### 5.4 前端 WebSocket 使用

```typescript

// 连接 URL: ws://host/api/monitor/ws?access_token=xxx

    + encodeURIComponent(String(accessStore.accessToken));

  autoReconnect: true,  // 自动重连
  heartbeat: false,

  if (newVal === 'OPEN') {
    send(JSON.stringify({
      e: 'joins',
      d: { names: ["ws:tag:monitor:server"] }

  switch (res.e) {
    case 'ws:event:monitor:server:host':   handleHostInfo(res.d);
    case 'ws:event:monitor:server:cpu':    handleCpuInfo(res.d);
    case 'ws:event:monitor:server:mem':    handleMemInfo(res.d);
    // ...
  }
```

```typescript
async function authLogin(params) {
  // 1. 密码 MD5 加密
  params.password = md5(params.password);
  // 2. 调用登录 API → 获取 token
  const { accessToken } = await loginApi(params);

    getAccessCodesApi(),

  await router.push(userInfo.homePath || DEFAULT_HOME_PATH);
}
```
